## 目的

- 最低限の評価（テスト入力セット）を作り、改善前後の差分を説明できるようにする

## ゴール（完了条件）

- テスト入力セットを `--suite` で実行できる
- 結果JSONを `--out` に出力できる

## 機能要件

コマンド

- `python -m day09.app` で起動できること（モジュール名は固定）

必須オプション

- `--suite`：テスト入力セットのパス（必須）

任意オプション

- `--out`：評価結果の出力パス（デフォルト `day09/result.json`）
- `--timeout-sec`：1ケースあたりのタイムアウト（整数、デフォルト `30`）

出力

- 正常時：標準出力にサマリ（成功/失敗件数）を出す
- 失敗時：標準エラーにエラーメッセージを出す

終了コード

- 正常終了：`0`
- 入力不備（`--suite` 不正など）：`2`
- 実行失敗：`1`

受け入れ基準

- `--suite` で指定したケースを順に実行できる（まだ中身はスタブでもよい）
- `--out` にJSONを出力する（成功/失敗の一覧を含める）

## 実行方法

### テスト入力セットの実行方法

```bash

# 出力先を指定

```

- テストケース設計（正常/異常/境界）  
　　テストは正常系、異常系、境界値の3分類で作成すると良い。  
　　正常系は期待通りに動くか、異常系は期待値通りに失敗するか、境界値は境目の値で挙動が切り替わるかを確認する  
　　異常系ではどのような例外か、出力されるメッセージは適切か、についても確認する
　　実装をなぞってケースを作成するのではなく、あるべき姿をケースに起こす
- 失敗分類（検索/推論/構造化/ツール/ガード）  
　　テストが失敗した原因を種類ごとに整理すること  
　　検索：必要な情報が見つからない  
　　推論：AIや処理の判断結果が不適切  
　　構造化：JSONなどの形式が不正  
　　ツール：外部ツールや処理の実行失敗  
　　ガード：危険・不正な入力を拒否できない
- 評価の記録方法（表、ログ、簡易集計）  
　　テスト結果を後から確認・比較できる形で残す方法  
　　表：ケースごとの結果を一覧で管理する  
　　ログ：実行中の詳細情報を記録する  
　　　　　ケースIDや処理の状態、失敗理由、エラーコードなどを記載します  
　　簡易集計：全体の合格・失敗件数をまとめる
