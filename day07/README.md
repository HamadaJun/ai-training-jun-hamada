## 目的

- LangGraphで状態遷移を持つ処理フローを実装できるようにする
- stateに途中結果を保持し、デバッグ/説明ができるようにする

- 分岐が最低2パターン発生する

## 機能要件

コマンド

- `python -m day07.app` で起動できること（モジュール名は固定）

必須オプション

- `--text`：ユーザー入力（文字列、必須）

任意オプション

- `--mode`：分類方式（`llm` / `rule`、デフォルト `rule`）

出力

- 正常時：標準出力に結果（文章）を出す
- 失敗時：標準エラーにエラーメッセージを出す

終了コード

- 正常終了：`0`
- 入力不備：`2`
- 実行失敗：`1`

受け入れ基準

- 入力に応じて分岐が最低2パターン発生する
- どの分岐に入ったかがログで分かる
- 分類不能時はデフォルト分岐へ入る（または明示的に失敗する）

## リサーチメモ（任意）

調べたURLや、理解した要点をメモしてください。

- LangGraphの基本（state/node/edge、条件分岐） 
　　LangGraphは処理途中のデータを保持する辞書形式の状態データのこと  
　　　・State（状態） … グラフ全体で共有される1つの辞書。ノード間の唯一の通信手段  
　　　・Node（ノード）… 状態を受け取り、更新分を返す関数。実際の処理はここ  
　　　・Edge（エッジ）… 次にどのノードへ進むかの経路  
　　条件分岐  
　　　・機械的な条件分岐  
　　　・LLMに分類させて分岐  
　　　・ツール呼び出しの有無で分岐  
- state設計（何を保持するか）  
　　stateはノード間で受け渡す必要があるものだけを置く場所（グローバル変数）でローカル変数で済むものは入れない  
　　他にも以下の物は入れないようにする
　　　・APIキーなどの認証情報  
　　　・バイナリファイルや大きなHTMLは保存コストが上がるもの（入れるのはパスだけ）  
　　　・ほかの値で計算できるもの  
　　　・DBの接続情報
　　　・検索結果の上位を何件取るか(top_k)のような実行ごとに変わらないもの  
- ログの入れ方（どのノードで何が起きたか）
　　ノードごとに書くのではなく、一か所に集中させる  
　　記録するのは「何を書き換えたか（キー名）」と「量」であって、値そのものではない  
　　どの経路を通ったかだけではなく、なぜそちらを選んだかを残す  

## 付録：設計メモ

### 状態設計（state）

最低限、以下の情報をstateに持たせてください。

- `input`：ユーザー入力
- `intent`：分類結果
- `output`：最終出力
- `errors`：エラー情報（あれば）

### 分岐条件

以下のいずれかの方式で分岐してください。

- 方式A：LLMで分類して分岐（例：`rag` / `summarize` / `plan`）
- 方式B：ルールで分類して分岐（キーワード、正規表現など）

### 実装内容（例）

`day07/` 配下に、次のLangGraphを実装します。

- ノード1：入力を分類する（intentを決める）
- ノード2：intentに応じて処理を分岐する
  - 例：RAG（仮でもOK）/ 要約 / タスク分解
- ノード3：最終出力を整形する

最低限、分岐が2つ以上あること。
